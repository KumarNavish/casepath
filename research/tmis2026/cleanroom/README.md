# Clean-room re-derivation of the fresh2 tenancy reference

**Why.** The Study 3 tenancy reference (`fresh2/tenancy/data/references/*.json`, field `document_states`) was
computed by the production rule engine (`harness/casepath_tenancy.py::plan_from_verified_exact`) from each claim's
designed fact states under the silence policy. A referee objects that the reference therefore comes from the engine
that the tested product implements. Response: two evaluators who never see the engine, its outputs or the
reference re-derive the document states from the rule text alone; their references are then compared with the
registered one and with each other.

**Who may read what.** The person running the exercise gives each evaluator only the path to `bundle/` and to
the evaluator's own folder.

| Path | Content | Evaluators A and B |
|---|---|---|
| `bundle/` | `TASK.md`, `SCHEMA.md`, `rules.json`, `claims.json` | may read; the only thing they may read |
| `evaluator_a/`, `evaluator_b/` | each evaluator's own `evaluate.py`, `reference.json`, `SEMANTICS.md` | each works only in its own folder and must not read the other's |
| `registered_reference.json` | the registered reference (claim id -> document type -> state), copied from `fresh2/tenancy/data/references/*.json` `document_states` | **must not read** |
| this README, the rest of the repository | | **must not read** |

The evaluators must not run or read any other code or data in this repository, must not call a model, and work
independently. The comparison (agreement of A, B and the registered reference, and the cause of every
disagreement) is made afterwards by someone else; nothing in this folder computes it.

**What the bundle contains.**

- `rules.json`: for each dispute type, what the prompt-based designs of Study 3 were shown of a rule template
  (`harness/v2/tenancy_v2.py::rules_block_v2`, the `rule_packs` entries): template id, title, prose content
  including the silence-policy clause, and the process catalogue (nodes, transitions with conditions, documents
  with condition, requirement class and steps) without its `assertion` fields; plus the condition catalogue (fact
  names only, `FAMILY_FLAGS`), which the designs were also shown and without which the fact names in `claims.json`
  would be unexplained.
  Left out of the source file `fresh2/tenancy/rules/static-rule-templates-v3-silence.json`: the top-level
  `contract`, `model_visibility`, `case_activation_values_included` and `rule_semantics` fields (a statement of
  evaluation semantics chosen by us; the designs never saw it); the per-template `clauses` list (the same text as
  `content`, split with offsets and hashes; not shown to the designs); every `assertion` (a generated sentence
  restating a row; not shown to the designs). Also left out, although the designs' prompt contained them: the
  `presumed_when_unmentioned` verdict table of the silence policy, `operational_condition_questions` (which says how
  receipt of a termination notice is to be judged) and `required_facts_by_document`: these are our own operational
  semantics or content-sufficiency descriptions, not rule text, and sufficiency is given per attachment.
- `claims.json`: for each of the 96 claims, the designed state of every fact (`stated_true`; `denied` from
  `stated_false`; `not_mentioned` from `absent` (branch facts) and `unmentioned` (defining event);
  `raised_and_left_open` from `open`) and the supplied attachments with document type and designed sufficiency.
  Not included: claim and attachment texts, family, subset labels, the true value of the open fact, the
  answered plan, wording style (`expression`), the blind-check readings and every reference field.
- `TASK.md`, `SCHEMA.md`: the instruction and the formats.

The bundle was generated by a one-off script (not kept in the repository) that read only the template file and
the reference files named above.

**Alternative readings (added 2026-11-12).** After both evaluators had delivered, evaluator B was asked to write
references under four readings of the rule text that the evaluators had rejected (`evaluator_b/reference_alt_A1.json`
to `_A4.json`, and `_all.json` with the four together; described in `evaluator_b/SEMANTICS.md`). They are inputs to
the reading-sensitivity analysis (`analysis/study3_feedback.py`, F5). They are not independent evidence: they
state how far the result depends on our reading of the rule text.

**A breach of the evaluator's restrictions, recorded as reported.** While writing the alternative references,
evaluator B copied its own `reference.json` into the session's scratch directory to compare bytes later, deleted
the copy, and listed that directory to confirm the deletion. The listing showed the names of other files of this
work (among them `build_cleanroom.py` and `oracle`). By its report it opened none of them. This happened after
its `reference.json` had been delivered and hashed (sha256 `2350c0ea…db294`, unchanged afterwards), so the
clean-room comparison is not affected; the alternative references were written to an instruction and are not
blind in any case. The evaluator's sessions are AI sessions; nothing here was checked by a person.
