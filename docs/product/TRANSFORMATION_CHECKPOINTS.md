## Baseline diagnosis

The prior workbench already has exact source previews, persisted review activity, request drafts, tri-state conditions, and an attractive restrained visual language. It is worth preserving. Its most consequential gap is functional: a saved handler condition note is intentionally inert. The existing `test_handler_condition_note_is_recorded_withdrawn_and_replayed` requires the accepted assessment to remain unchanged. A new explicit process-edit event is therefore necessary; rewriting historical note semantics would corrupt replay. The legacy next-action text is also domain-specific rather than entirely graph-derived.

## Design direction

The handler's job is to decide what needs doing and why, then correct an inaccurate process without restarting. The domain is claims, sources, procedural steps, prerequisites, branching, missing documents and review. Retain the existing paper-white, ink-blue, slate, amber and green language. Use a quiet step-and-dependency view with an adjacent contextual inspector. The distinctive interaction is the visible chain from edited condition through affected steps to changed requests. Keep chat, decorative graph canvases and abstract activity counters secondary to completed work and actionable artifacts.

## Efficiency and evidence boundaries

Propagation, validation, checksums, extraction of known fields and tests use deterministic code. The core task requires architecture and interacting-cause debugging; Jev would not replace that reasoning. No paid inference or new product model dependency is introduced. Model quality, legal correctness, real-claim suitability, enterprise access controls and customer willingness to pay require separate evidence. Local fixture success cannot establish those claims.
